# Mobile parity status

Implementation checkpoint: 2026-09-20. Mobile and desktop use the same React app, typed client, product schemas, characters, project/file concepts, and responsive layout. The mobile host owns ordinary files and foreground execution; the desktop daemon owns processes and background work. No migration is needed for the unreleased mobile app.

## Execution and recovery

Every side-effecting model tool has a durable started record before execution and a durable result before another model/tool call. JSON examples, fenced blocks, truncated envelopes and unlisted tools cannot execute. The foreground loop is bounded, and handoff depth/count limits prevent an unbounded crew chain. Role, project and step restrictions are checked again at execution time.

The raw native adapters remain text providers. Tool use is implemented by the product runtime's strict completion protocol. Passing fake-provider or tiny-GGUF tests demonstrates routing, persistence, isolation and cancellation; it does not demonstrate that a real model follows the protocol reliably. System AI availability and usefulness need evaluation on supported hardware.

Ordinary client messages can deliver one-way crew feedback into an existing project conversation, preserving sender identity and structured file-repair hints. Hints never expand the recipient's live role, project, or step authority. Automatic reply chains and ad-hoc checked-deliverable scripts remain unavailable; task completion gates own checked transitions. File tools share desktop append, replacement, line-range, ambiguity, and newline semantics. Editor transforms use the configured Klerk and the same prompts and output handling as desktop; generated text stays in the editor for review before Apply.

The shared task composer saves task-linked drafts as ordinary project files. Reopening and “Use again” preserve their task address; sending to a different task or conversation fails before any message is committed. Pause and Cancel revoke task, model, and script execution even when saving the requested status fails. The save failure stays visible, and recovery does not replay the interrupted work.

Task runs checkpoint before dispatch and inspect completion gates. Execution mode is resolved once using desktop’s generalist setting; local auto remains stepwise. Explicit generalist tasks pin one owner, preserve human/specialist assignments, and reuse compatible task transcripts. Model/provider changes, running sessions, and context-failed transcripts require a fresh session. Conversations carry a host-owned activation identity: routing back to the same step revokes its previous turn and script effects. Both new and reused task conversations wait for that activation’s entry hooks to finish. Approving gate scripts can route and persist a handoff; broken or malformed gate scripts pause without spending a deliverable attempt. Continuous foreground execution advances through approved steps, retaining per-activation lifecycle-hook journals; it stops at human steps, unanswered questions, failures, cancellation or execution limits. Successful hooks are not replayed after reopening; interrupted hooks require explicit retry. App backgrounding cancels active work. Interrupted turns, scripts and task runs remain inspectable and never resume automatically. An uncertain save blocks further work until persistence recovers. A force-kill can lose streaming text since the last durable checkpoint, but cannot trigger automatic replay of a recorded action.

The task SDK uses those same transitions: a rejected gate returns `held`, and approved advancement runs exit hooks before a snapshot-checked commit. Completion scripts execute as isolated children with their own step identity, parent audit links, live authorization, and shared cancellation/budget ceilings. Lifecycle/gate scripts cannot mutate task structure or advance their own checkpoint. Task and script deadlines count awake time, dispose their timers, and still honor immediate native background cancellation.

The ZIP format follows the desktop manifest and entity layouts. Import validates names, sizes, paths and records before staging a review; explicit replacement uses the same crash-recoverable transaction mechanism as other product writes. Selected portable preferences can be restored; credentials, security settings, device paths, native model weights and derived indexes are excluded. Current limits are 16 MiB per file, 64 MiB expanded content, 5,000 entries and a 72 MiB archive.

## Running and checking

`pnpm android` and `pnpm ios` rebuild the shared product, sync installed native assets, and open the platform IDE. Select an ARM64 Android emulator or an iOS simulator/device, then Run. Native engine builds and platform prerequisites are described in the [mobile README](../packages/mobile/README.md).

Use `pnpm mobile:build`, `pnpm mobile:check`, `pnpm mobile:test:scripts`, and `pnpm mobile:test:android` for the portable, real-QuickJS and Android checks. The [native CI workflow](../.github/workflows/mobile-native.yml) also defines pinned-engine and iOS simulator checks. Its Android job compiles the real ARM64 production payload and test APK; it does not claim emulator execution on the Linux hosted runner.

Local verification includes a full core run of 1,703 tests, 146 client tests (one separate existing skip), and passing coverage of 2,441 shared UI tests through a full run plus a two-file retry, and focused desktop regressions for the extracted execution, editing, and transform helpers. The mobile check passes 233 core/runtime tests and 52 mobile tests. The rebuilt production browser workflow passed 21 layout/workflow checkpoints, including accessible names and affected 44px targets; real QuickJS browser execution passed 36 checks, including repeated task setup and stale-conversation rejection. Android's refreshed full native suite passed 33 cases with one explicit real-provider quality skip. iOS AppSmoke passed its four enabled integration tests with quality explicitly skipped. After the task-draft, cancellation, model-identity, and eval-evidence fixes, packaged offline eval contracts passed 23 assertions and six reload checks on each platform, verifying the exact test-source and production entry digests. Both native reports verify restoration of original product files and model inventory; an independent iOS comparison also matched its complete product tree before the smoke suite and after the contracts. These contracts exercise compilation, QuickJS, shared question UI, native storage, isolation, recovery, message metadata, targeted file editing, and generalist continuity. Fixed test-only provider responses and synthetic llama.cpp fixtures prove mechanics only. Remote CI has been defined but was not dispatched from this work.

The [accessibility review](../reports/a11y-review-20260920-1505.md) records the shared view audit, confirmed fixes, browser evidence, and remaining assistive-technology checks. The final accessibility UI bundle also passes both native integration suites and both 23-assertion/six-reload contract runs, with original data restored exactly. The unsigned Android APK/AAB and iOS archive each verify all 694 compiled web files byte-for-byte against the same production entry. The real-provider quality launcher was blocked by a new desktop eval holding the shared device lock; no mobile model-quality result has been produced. It did not bypass the lock or run inference.

The catalog schema freshness check currently fails against pinned Gilde 0.1.67 because the generated gezel-template schema lacks the two new mobile provider values. The generated update in the sibling Gilde checkout passes full structural validation; publishing it and updating the pin remains a separate release prerequisite. No catalog assertion has been weakened or bypassed.

The new packaged eval launcher (`pnpm mobile:eval`) separates deterministic native contracts from real-provider quality runs and retains canonical unsupported scenarios in its coverage report. `pnpm mobile:package android|ios <build-number>` creates unsigned release artifacts using installed toolchains; signing and store submission remain external release work.

Release requires the remaining device/quality and distribution gates above. The current implementation is a working foreground offline product, not complete desktop parity.
