# Pull Request Review — PR #28: fix: More CLI work, UX update

## Summary
Large PR across 169 files (+6,746 / −1,465) touching CLI TUI ownership model, `gezel stop` semantics, managed workspace write policy, model download flow, eval framework artifact routing, role-based naming, Windows headless spawn options, CLI detection, voorman self-escalation, catalog WIP feature gate, task step transition durability, and MCP artifact collision redirects. No existing PR comments. The changes are cohesive — they advance the CLI TUI into a first-class interactive surface while hardening the service layer for edge cases (Windows console windows, one-shot timeouts, step-transition replays). One breaking CLI behavior change needs attention.

## Findings
| # | Severity | File | Line | Finding | Recommendation |
|---|----------|------|------|---------|----------------|
| 1 | major | `packages/cli/src/bin/gezel.ts` | 348–399 | `gezel stop` semantics changed from "stop the daemon" to "hard stop AI work + Reactive mode". The old behavior is now `gezel stop --daemon`. This is a **breaking change** for any existing scripts, CI, or user muscle memory that ran `gezel stop` to shut down the daemon. The README is updated but no deprecation path or warning exists. | Either (a) add a deprecation warning on `gezel stop` without `--daemon` that fires for a release cycle before flipping, or (b) document this as a breaking change in the release notes and bump the CLI minor version. At minimum, the `--help` text should mention `--daemon` prominently. |
| 2 | minor | `packages/cli/src/connection.ts` | 187–197 | `cliUserDaemonEnv` strips `GEZEL_PORT`, `GEZEL_SERVICE_ROLE`, `GEZEL_SYSTEM_SCOPE` from inherited env but passes through all other `GEZEL_*` variables. If a parent process sets `GEZEL_TOKEN` or `GEZEL_HOME` to unexpected values, the child daemon inherits them. The rest-of-env spread (`...rest`) is a wide net. | Consider an allowlist or explicit strip of known GEZEL_* service-host variables rather than a denylist of three. Alternatively, add a comment naming the rationale for the current three. |
| 3 | minor | `packages/cli/src/tui/active-access.ts` | 31–36 | `activeAccessMode` uses `Reflect.get(GezelCore, 'resolveGezelWorkspaceAccess')` as a compatibility shim for CLI 1.0.1 shipped against core 1.0.0. This is pragmatic but fragile — a future core version that removes or renames the export silently falls back to the inline calculation, which may diverge. | Add a `log.warn` when the compatibility path is taken, so users on mismatched versions see a nudge to align. |
| 4 | minor | `packages/service/src/chat/manager.ts` | 2553–2554 | `emergencyStopChats` now calls `this.resetClient()` to unload local engines. This is correct behavior (matches the new "hard stop" semantics), but the method is also called from the HTTP route, which persists `reactive` config. If `resetClient()` fails partway (e.g., an engine refuses to shut down), the config is already flipped to reactive but engines may still be running. | Wrap the `resetClient()` call so a partial failure still returns success counts but logs the engine shutdown failure. The current `await` will propagate any error to the caller. |
| 5 | minor | `packages/service/src/tasks/manager.ts` | 2117–2128 | Step transition durability: the state-machine write now happens **before** role resolution, with a second write after. This correctly prevents duplicate transitions on MCP retry, but the two writes mean a crash between them leaves the task on the correct step but without the resolved `suggestedGezelId`. The recovery sweep comment says it can pick this up, but is that actually implemented? | Verify that the task runner's recovery sweep re-resolves `suggestedRole` for steps with `suggestedGezelId: undefined` but `suggestedRole` set. If not, add it. |
| 6 | minor | `evals/src/craftbooks/scenario.ts` | 818–844 | Artifact deliverable checks are filtered to an allowlist of check kinds. The list is hardcoded and doesn't include every check kind — if a new check kind is added to `GateCheckSchema`, it won't work on artifact deliverables until someone remembers to add it here. | Derive the allowlist from the check schema or add a lint that cross-references `GateCheckSchema` discriminants against this list. |
| 7 | nit | `packages/cli/src/tui/commands.ts` | 39–52 | `PROJECT_PERMISSIONS` is a `const` array but `parseProjectPermissionName` does a case-insensitive match (`.toLowerCase()`). The names in the array are lowercase, so this works, but the description strings are mixed case and the function name says "parse" not "normalize". | Rename to `normalizeProjectPermissionName` or make the match case-sensitive for consistency with other CLI parsers. |
| 8 | nit | `packages/service/src/chat/model-tool-name-contract.ts` | 278–290 | `partitionModelToolNameFindings` is simpler than the old `partitionPinnedGildeDebt` (good), but the function name doesn't reflect that it now only partitions by `category === 'generated-catalog'`. A future category might need different treatment. | Consider naming it `partitionFindingsByOwnership` or similar to signal the intent rather than the implementation. |
| 9 | nit | `packages/ui/src/components/EngineStatusPill.tsx` | 826 | The `statusText` line is now 140+ characters with a ternary chain. Hard to review visually. | Extract to a named helper or build with array join. |
| 10 | nit | Multiple `package.json` files | various | All `keywords` and `files` arrays collapsed from multi-line to single-line. Consistent but makes future `git blame` noisy for unrelated changes. | Consider keeping multi-line format for maintainability, or accept this as style normalization. |

## Verdict
Verdict: request-changes

Finding #1 (breaking `gezel stop` semantics) needs a deprecation path or explicit breaking-change documentation before this ships; the remaining findings are addressable but don't block on their own.
